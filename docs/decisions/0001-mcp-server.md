# 0001 MCP サーバーで、AI から作品を作れるようにする

状態: 決定（2026-10-10 承認）。

## 状況

Claude などの AI に、Mirage Composer の作品（`.mcomp`）を作らせたい・直させたい。今は、AI が作品を扱うには、こちらがテスト用のコードを書いて描画を確かめるしかない。

MCP（Model Context Protocol）は、AI のクライアント（Claude Code、Claude Desktop など）から外部の道具を呼ぶための標準の仕組み。MCP サーバーを用意すれば、AI が次のことを自分で回せる。

- パッチを置き、つなぎ、値を決める。
- 描いた結果を画像で見る。
- 問題（シェーダーのエラー、見つからない画像）を読んで直す。

### 調べて確かめたこと（2026-10-10）

- **エンジンは別の部品になっている**。描画エンジン MetalComposerKit は、エディタの UI を含まないライブラリ。Graph、Patch、Evaluator、FrameRenderer など作品の編集と描画に要る型は、`package` の公開範囲で同じパッケージの中から使える。外向けの API は、再生用の `CompositionPlayer` だけ。
- **画面なしで描ける**。テストでは、ウィンドウを出さずにオフスクリーンのテクスチャへ描いて画素を読んでいる（Cube、Sphere、パーティクル、Text Image などで確認済み）。
- **MCP の公式 Swift SDK**（[modelcontextprotocol/swift-sdk](https://github.com/modelcontextprotocol/swift-sdk)、0.12.1、2026-05-07）がある。
  - ライセンスは MIT から Apache-2.0 へ移行中。
  - 依存が多い。swift-nio、swift-log、swift-system、eventsource に加えて、swift-docc-plugin を **ブランチ（main）指定**で使っている。swift-tools-version は 6.1。
- **このパッケージは OnomFlow から依存されている**（MetalComposerKit を使う）。SwiftPM は、使わない製品の依存も含めてパッケージ全体の依存を解決する。そのため、ここに SDK を足すと OnomFlow の依存解決にも入る。ブランチ指定の依存を含むパッケージは、バージョン指定で依存されると解決に失敗する恐れがある。
- **MCP の stdio 通信は単純**。1 行 1 メッセージの JSON-RPC 2.0 で、サーバーに要るのは `initialize`、`tools/list`、`tools/call`、`ping` と通知の受け流し程度。描画結果は `image` 型のコンテンツ（base64 の PNG）で返せる。仕様の最新版は 2026-07-28。

## 選択肢

| | A. ファイルを扱う MCP サーバー（独立した実行ファイル） | B. エディタのアプリに組み込む |
| --- | --- | --- |
| 構成 | このパッケージに実行ファイル `mirage-mcp` を足す。AI のクライアントが起動し、stdio で話す。作品はメモリ上で編集し、ファイルに保存する | 起動中のエディタに MCP の窓口を置き、開いている作品をその場で編集する |
| 既存への影響 | エディタのアプリと App Store 版には入れない。アプリのコードは基本的に変えない | アプリの中に通信の仕組みが入る。Mac App Store 版はサンドボックスのため接続方法に工夫が要る。iOS では難しい |
| 人との協調 | エディタで開いている作品とは別に扱う（エディタは自動で読み直さない） | 編集が画面に即反映され、Undo も効く |
| 実装の量 | 小〜中 | 中〜大 |

### A の中での選択：MCP の実装

| | A1. 公式 Swift SDK を使う | A2. stdio の JSON-RPC を自前で書く |
| --- | --- | --- |
| 依存 | swift-nio ほか多数。ブランチ指定の依存を含む | なし（Foundation だけ） |
| OnomFlow への影響 | 依存解決に入る。失敗する恐れがある | なし |
| 仕様への追従 | SDK が追う | 自分で追う（使う範囲は狭い） |
| 置き場所 | 別パッケージにすれば影響は避けられるが、`package` の型が使えず、編集用の API を外向けに整える必要がある | 同じパッケージに置け、`package` の型をそのまま使える |

## 決定

**A（独立した実行ファイル）を A2（自前の stdio JSON-RPC）で作る。**

- エディタのアプリ、App Store 版、OnomFlow に影響を与えずに足せる。
- 同じパッケージに置くので、パッチを追加すれば MCP 側でも自動で使え、両者がずれない。
- 使う MCP の範囲（stdio、tools、image コンテンツ）は狭く、依存なしで書ける。将来 SDK の依存が落ち着いたら、差し替えを検討する。
- B（アプリへの組み込み）は、A の道具をそのままアプリにつなぐ形で、必要になったら足す。

### 道具（tools）の最初の範囲

| 道具 | 内容 |
| --- | --- |
| `list_patches` | 置けるパッチの一覧。種類 ID、名前、説明、分類、入出力（キー、名前、型、既定値、範囲、選択肢） |
| `new_composition` / `open_composition` / `save_composition` | 作品を新しく作る・開く・保存する（パスは呼び出し側が指定） |
| `get_graph` | 今の作品の中身。パッチ（ID、種類、名前、位置、既定と違う値）とつながり。マクロの中は ID の道筋で指定 |
| `add_patch` / `remove_patch` / `rename_patch` | パッチを置く・消す・名前を付ける（マクロの中にも置ける） |
| `connect` / `disconnect` | ポートをつなぐ・外す（型の変換はエディタと同じ規則） |
| `set_params` | 入力の値を設定する。値はわかりやすい JSON（数値、真偽、文字列、色は `[r, g, b, a]`） |
| `render` | 指定した時刻（複数可）・大きさで描き、PNG 画像と問題の一覧を返す |
| `problems` | 問題の一覧（シェーダーのエラー、見つからない画像、知らないパッチなど） |
| `measure` | 指定した時間を描いたときの 1 フレームの計算時間（平均・最大） |

時刻は作品の時刻（秒）で、パーティクルなども含めて同じ時刻なら同じ絵になる（0.2.0 からの性質）。

### 安全のための制限（2026-10-10 追加）

`mirage-mcp` はサンドボックスなしで、使う人の権限で動く。AI が読んだ文書などに紛れた指示で操作させられる恐れもあるので、道具ができることを次のように絞る。

- **保存は `.mcomp` だけ**：拡張子が `.mcomp` 以外のパスには書かない（拡張子がなければ付ける）。既にあるファイルは `overwrite: true` のときだけ上書きし、フォルダには書かない。
- **画像を読む場所を限る**：Image Importer が読めるのは、作品の保存先フォルダの中と、起動時に `--allow-images <フォルダ>` で許可したフォルダの中の画像ファイルだけ。シンボリックリンクと `..` は解決してから確かめる。描画の前にもすべての Image Importer を確かめ直す。
- **マイクを使うパッチは使えない**：Audio Input と Audio Spectrum は置けず、一覧にも出さない（エディタの外でマイクが動くのを避ける）。
- **描画に時間の上限**：1 回の `render` が 15 秒を超えたら打ち切る。ただし確かめるのはコマとコマの間なので、1 コマだけで 15 秒を超える作品は、そのコマが終わるまで止まらない。

## 進め方

1. **最小の縦切り**：`mirage-mcp` の骨組み（initialize、tools/list、tools/call）と、`list_patches`、`new_composition`、`add_patch`、`connect`、`set_params`、`render`、`save_composition`。
   - Claude Code に登録し、「赤い円を描く作品を作って保存」が通ることを確かめる。
2. **読む・直す**：`open_composition`、`get_graph`、`remove_patch`、`disconnect`、`rename_patch`、`problems`。
   - 既存の作品（デモやユーザーの作品）を説明させ、直させる。
3. **性能を見る**：`measure`。重い作品の原因を AI に調べさせる。
4. **配布**：README に登録方法を書く。必要なら署名・公証した実行ファイルを GitHub のリリースに置く。
5. **（必要になったら）エディタの読み直し**：開いている作品のファイルが外から変わったら、確認のうえ読み直す。

## 影響

- パッケージに実行ファイルの製品が 1 つ増える。OnomFlow など Kit だけを使う側は、その製品をビルドしないので影響しない。
- 道具の説明（パッチの入出力の一覧）を返すために、Kit に小さな追加が要るかもしれない。アプリの動作は変えない。
- AI がファイルを書き換えている間に、同じ作品をエディタで開いたまま保存すると、AI の変更を上書きする。最初は「AI が作る → エディタで開いて確かめる」の順で使う。
- 通信は stdio だけで、ネットワークには出ない。ファイルは呼び出し側が指定したパスだけを読み書きする。
